# RAG для трудового законодательства РФ

Небольшой учебный проект по созданию RAG-системы для поиска информации в **Трудовом кодексе РФ** и формирования ответов на вопросы пользователя.

Система учитывает структуру исходного документа при разбиении на чанки, использует **гибридный поиск BM25 + semantic search**, а найденный контекст передаёт LLM для формирования ответа.

В качестве интерфейса также реализован Telegram-бот.

## Как работает

```text
Трудовой кодекс РФ (.docx)
        ↓
Структурный parsing
        ↓
Часть → Раздел → Глава → Статья
        ↓
Chunking внутри статей
        ↓
SentenceTransformer embeddings
        ↓
Pickle index
        ↓
Пользовательский вопрос
        ↓
Query transformation
        ↓
 ┌───────────────┬───────────────┐
 │ Semantic      │ BM25          │
 │ search        │ search        │
 └───────┬───────┴───────┬───────┘
         └───────┬───────┘
                 ↓
          Hybrid ranking
                 ↓
        Агрегация по статьям
                 ↓
          Релевантные статьи
                 ↓
              LLM
                 ↓
             Ответ
```

## Основные компоненты

### Структурный chunking

Документ разбирается с учётом его иерархии:

```text
Часть
 └── Раздел
      └── Глава
           └── Статья
                ├── chunk
                ├── chunk
                └── ...
```

Если статья достаточно короткая, она берется одним цельным фрагментом. Более длинные статьи дополнительно разбиваются на части.

Каждый chunk сохраняет metadata:

* часть;
* раздел;
* глава;
* статья;
* уникальный идентификатор.

Это позволяет при поиске работать не только с отдельными фрагментами текста, но и агрегировать результаты на уровне статей.

### Гибридный поиск

Используются два способа поиска:

* **BM25** для лексического поиска;
* **semantic search** на основе cosine similarity между embeddings.

Для получения embeddings используется `intfloat/multilingual-e5-large`.

### Query Transformation

Перед этапом поиска чанков, пользовательский вопрос может быть преобразован LLM в более формализованный запрос, близкий к стилю нормативного текста.

Например, разговорный вопрос преобразуется в формулировку, содержащую юридические термины и условия, которые могут лучше совпадать с текстом законодательства.

Для проверки влияния этого этапа предобработки был проведен тест на небольшом массиве вопросов с преобразованием запроса и без него.

### Агрегация по статьям

Поскольку одна статья может состоять из нескольких чанков, после гибридного поиска результаты группируются по номеру статьи.

Для каждой статьи используется максимальный score среди ее чанков.

Таким образом, несколько релевантных чанков одной статьи не занимают несколько позиций в итоговой выдаче.

### Генерация ответа

Найденные фрагменты передаются LLM вместе с исходным вопросом.

Модель получает инструкции:

* отвечать только на основе найденного контекста;
* не придумывать информацию;
* использовать формулировки, близкие к тексту закона;
* объединять информацию из нескольких статей при необходимости;
* указывать номера использованных статей.

## Оценка

Для оценки retrieval-компоненты был подготовлен небольшой тестовый набор вопросов с заранее известными релевантными статьями.

Использованы метрики:  
* **Hit Rate@5** — попала ли правильная статья в топ-5;
* **MRR@5** — насколько высоко в выдаче находится правильная статья.

### Результаты

| Query Transformation |      Hit Rate@5 |      MRR@5 |
| -------------------- |----------------:| ---------: |
| Без преобразования   |             85% |     0.6017 |
| С преобразованием    |         **95%** | **0.6242** |

На данном небольшом тестовом наборе query transformation увеличил Hit Rate@5 с **85% до 95%** и немного улучшил MRR@5.

Результаты являются ориентировочными из-за небольшого размера тестовой выборки.

## Telegram бот

Для проекта реализован Telegram-интерфейс.

Пользователь отправляет вопрос, после чего бот:

1. преобразует запрос;
2. выполняетгибридный поиск;
3. выбирает наиболее релевантные статьи;
4. передает найденный контекст LLM;
5. возвращает ответ и использованные статьи.

Модель и индекс загружаются один раз при запуске бота.

## Хранение индекса

Отдельная векторая база данных не используется.

Индекс сохраняется в обычный `pickle`-файл и содержит:

```python
{
    "chunks": [...],
    "embeddings": [...]
}
```

Для небольшого статического корпуса такой подход позволяет сохранить проект простым и не добавлять дополнительную инфраструктуру.

## Запуск

Установить зависимости:

```bash
pip install -r requirements.txt
```

Создать `.env`:

```env
BOT_TOKEN=...
GROQ_API_KEY=...
HF_TOKEN=...
```

Основной pipeline запускается через:

```bash
python run.py
```

`run.py` сначала создаёт индекс, если его ещё нет, а затем запускает CLI для вопросов.

Для оценки retrieval-компонента:

```bash
python -m src.evaluate
```

Telegram-бот запускается отдельно:

```bash
python -m src.telegram_bot
```

## Ограничения

Проект является учебным экспериментом и не предназначен для использования в качестве профессиональной юридической консультации.
